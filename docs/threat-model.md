# Threat model — Authent'INT (B6)

What an attacker wants, what stops them, where the control lives, and the test that fails if the
control breaks. Paths are relative to the repo root; `A/` = `apps/auth-server/`,
`M/` = `apps/mock-services/`. Tests run with `make test` (auth-server, in the container) and
`cd apps/mock-services && uv run pytest`.

Scope: the docker compose stack (Caddy edge → auth-server → Postgres; mock resource servers; SPA).
Kubernetes is out of scope for this project (see "Known gaps").

## Known gaps

- **No MFA** (ADR §2): one factor (numéro fiscal + password). Lockout and rate limits reduce
  online guessing, but a phished password still logs in.
- **Access tokens cannot be revoked before `exp`**: they are self-contained JWTs checked offline
  by the resource servers. The 600 s TTL bounds the exposure. Refresh tokens and sessions are
  revoked immediately.
- **No network policy beyond compose networks**: Kubernetes is out of scope, so there is no
  NetworkPolicy. Isolation comes from the `edge`/`data` networks (Postgres is `internal`) and
  from Caddy being the only published port. `FORWARDED_ALLOW_IPS="*"` is acceptable only because
  auth-server publishes no port.
- **Future audit partitions need a REVOKE**: a new `audit_events` partition inherits the default
  privileges; the migration that creates it must `REVOKE ALL` from `authentint_app`
  (WARNING in `3c1e7a2b9d04_app_role.py`, and `test_the_partition_is_no_back_door` only covers
  the existing partition).
- **Login capacity is bounded by Argon2 CPU** by design (ADR §14): see `docs/load-report.md`.
  Beyond the per-IP and per-account limits, a large botnet can still saturate the login CPU (it
  cannot get through, but slows legitimate logins). Mitigation is at the edge (WAF, CAPTCHA), not built.
